# 家簿 · 产品需求

> 当前版本：v0.6（2026-10-26）。本文只描述产品需求与已确认的产品规则；技术实现见 [工程文档](../README.md#工程)。

## 1. 一句话

首版做成一个**以聊天为首页、可离线暂存的 Android App**：从设置到日常使用都通过与 AI 对话完成；信息明确就直接记账，缺项或识别不确定才追问；记录可改可撤。

## 2. 核心方向

- **对话完成日常记录**：首页是与 AI 的对话窗口，也是最高频的界面。文字和图片都能直接发进来，由 AI 辅助录入；不以手工填表为默认流程，但保留手工编辑。也可以用自然语言快捷问数、查资料。
- **关注账户积累，不做预算管理**：用途账户可自由增减，按月拨入、支出扣减、剩余持续结转。
- **家庭资料能存也能查**：原图留存，AI 提取关键信息供查询和比较；内容以带类型的 JSON 组织，没有专用模板也能默认渲染，有专用模板则更准确。
- **3 个主界面**：聊天首页、总览（Dashboard）、历史 / 搜索，控制首版复杂度。
- **2 种范围**：家庭共享与私人空间，始终明确显示、切换和校验。
- **各自聊天，共享家庭记录**：两位家庭成员各自与 AI 聊天；家庭记录共享，私人空间内容仅自己可见。
- **离线使用**：没有网络时可以查看已同步到手机的记录；新输入的文字和照片先存在本机，显示为待处理，联网后再交给 AI 整理入账。
- **暂不接入外部接口自动拉取数据**（如银行账单），未来再考虑。

### 已确认的交互原则

- **信息明确就直接记好**：金额、真实付款账户和逻辑用途等必要信息齐全、能明确匹配时，AI 直接入账并回复简洁的记录卡，支持随时修改或撤销，**不要求每笔再点确认**。缺少关键信息，或图片中的金额、内容识别不确定时，先追问再记录。
- **首次设置也通过对话完成**：首次使用时，通过对话创建真实资金账户和逻辑用途账户，设置各自的起始余额，以及用途账户的每月拨入计划。从启用时开始记新账，无需补录此前明细。用户可以分次提供信息，AI 针对缺项追问；设置完成后展示账户摘要，之后仍可通过对话修改，也保留手工编辑入口。**起始余额只用于衔接已有资金，不算启用后的新增收入或消费。**

## 3. 首版界面：只做三块主界面

底部导航只保留**聊天、总览、历史**三项。家庭 / 私人范围是所有记录的共同属性，不另造一套平行界面；当前范围要在页面顶部和每张记录卡上都可见。

| 界面 | 内容 |
|---|---|
| **聊天首页**（默认入口） | 顶部切换“家庭 / 私人”；中间是对话与 AI 返回的记录卡；底部输入文字、拍照或选图。首次设置也在这里完成。 |
| **总览** | 先看真实资金账户与逻辑用途账户余额，再看近期变化、待处理的离线项目和家庭资料摘要。不以预算使用率或“剩余额度”为中心。 |
| **历史 / 搜索** | 统一检索账目与家庭资料，可按范围、成员、账户、标签、类型和时间筛选；进入详情后查看原图、变更记录，执行编辑或撤销。 |

### 记录卡是关键交互单位

一张卡只显示用户核对所需的信息：记录类型、金额或资料标题、真实账户、逻辑用途、家庭 / 私人范围、状态与时间。卡上直接提供“编辑”和“撤销”；撤销后保留变化记录。

记录状态：离线输入标为“待上传” → 上传后标为“待 AI 处理” → 完成后显示“已记录”。失败时保留本地内容并允许重试。

### 权限边界必须显式

家庭记录对家庭成员共享，私人记录只允许创建者本人查看。范围切换不仅改变筛选结果，也决定新记录写到哪里；**提交时由服务端再次校验**，不能只依赖客户端状态。

## 4. 三条关键流程（也是验收场景）

覆盖最常见、最不确定和无网络三种情况。

1. **信息明确的支出：直接记录**
   用户在“家庭”范围输入“午饭 68，信用卡，日常餐饮”。AI 能明确匹配金额、真实账户与逻辑用途时直接入账，返回记录卡；用户可立即编辑或撤销，不多一步确认。
2. **照片不确定：先追问**
   用户拍下一张视力检查单。App 先保留原图；AI 提取能确认的日期和数值，针对模糊字段或所属家庭成员提**一个**聚焦问题。用户回答后生成资料卡，仍可回到原图核对。
3. **离线输入：排队后同步**
   无网络时文字与照片写入本地队列并显示“待上传”，用户仍可查看已同步记录。联网后按顺序上传，进入“待 AI 处理”；成功后替换为正式记录卡，失败项保留并可重试，**不能静默丢失**。

## 5. 账户与记账规则

现实中常见的做法是用专门的银行账户对应不同用途（一一绑定）。家簿改为**在每笔记录上建立逻辑关联**：一个用途可以从不同银行卡支付，一张卡也能承担不同用途。

| 账户类型 | 含义 |
|---|---|
| **真实资金账户** | 银行、理财等账户，表达钱实际在哪里。支持真实支出、收入和账户间转账记录。 |
| **逻辑用途账户** | 为某类事情设立的“心理账户”，核心是持续变化的余额；不要求与某个真实账户或真实可用资金一一对应。 |

规则：

- **用途账户灵活管理**：用户可以新增、改名、调整或移除逻辑账户，并修改每月拨入计划。系统不预设固定账户清单。账户调整时保留历史账目与关联（具体移除方式待细化）。
- **按月拨入、持续结转**：每月通常拨入固定金额，可调整；自动执行可开关，执行日期可配置，默认每月第一天。未花完的余额累积，不按月清零。
- **月度设置是“拨入计划”，不是预算**：不存在“月额度”，只有持续结转的账户余额。定期拨入、额外调拨与支出都会改变余额。
- **一笔支出同时关联**真实付款账户和逻辑用途账户，分别更新余额，**消费只统计一次**；关联发生在记录上，无需账户一一绑定。
- **超支处理**：允许逻辑账户出现负余额，也支持从兜底 / 备用金逻辑账户调拨补足（**推荐调拨方案**）。
- **自由标签**：支出分类用标签，可预设衣食住行等粗粒度分类，不限定为固定分类树。
- **后续更正**：修改、删除或退款时，按正常逻辑增减相关账户余额，并留下操作 / 变化记录。
- **真实资金变化与逻辑调拨分别记清**：真实收入、真实账户间转账是各自的记录类型；每月拨入逻辑账户不等于真实收入或银行转账，逻辑账户间调拨也不产生消费。

展示重点是“现在有多少余额、钱怎样进出和累积”。没花完的钱留在原账户继续累积，这正是用户希望看到的积累结果。

### 示例：用一笔消费检验关联（虚构数据）

教育用途余额 200，要从某张银行卡支付 500。

| 方式 | 结果 |
|---|---|
| 保留负数 | 教育余额变为 −300；下月再拨入 2,000，余额变为 1,700。 |
| **备用金调拨（推荐）** | 备用金先调拨 300 给教育用途，再记录完整支出 500。教育余额为 0，备用金余额减少 300。 |

两种方式中，银行卡都只支付 500，总消费都只有 500；逻辑调拨不需要真实银行转账，也不重复计支出。

## 6. 家庭资料与可见范围

第一个场景是**家庭成员的视力检查**：留存当次文字和图片资料，方便以后查询、回看。其他资料类型后续逐步加入。

AI 整理方式（已确认）：

- 保留完整原图，同时提取能明确识别的检查日期与关键数值，归入相应家庭成员的检查记录。
- 支持查询上次检查时间、列出历次结果对比，并回到原图核对；不确定的内容标明或向用户确认。

内容组织：

- **内容带类型，默认渲染**：具体内容以 JSON 组织，每项保留名称、值和类型（文字、数字、日期、图片等），数值按需携带单位。没有专用模板时按内容类型用默认模板渲染，仍能完整记录、清晰展示。
- **专用模板按需增强**：可以为某类资料建立专用数据类型 / 模板，明确字段含义并使用更合适的布局（例如视力检查模板区分左右眼与检查项目），帮助 AI 更准确地整理。新资料**不要求**先有专用模板。
- **通用信息只描述记录本身及其归属**；“检查日期”等业务字段属于具体内容或专用模板，不作为所有资料的必填公共字段。

| 空间 | 规则 |
|---|---|
| **家庭空间** | 可以创建家庭空间并邀请其他人的账号加入；内容对该空间全部成员可见。 |
| **私人空间** | 每人同时拥有私人空间，内容仅自己可见。 |

## 7. 身份与权限

- 服务端为每位用户建立一个**不可变的内部用户 ID**，它才是聊天、私人空间、家庭权限和数据归属的真实身份。
- 首版**预建两个“用户名 + 密码”账号**：不需要邮件、短信服务或公开注册。密码只保存安全哈希；登录后由 App 在 Android 安全存储中保管会话。
- 忘记密码先由管理员人工重置；邮箱登录、手机号登录和自助找回留待以后。

## 8. AI 接入原则

- 采用**独立的家庭助手**，有自己的会话与家庭上下文。
- 服务端有自有的模型接口，支持更换模型或服务商，按配置切换与降级。
- **默认使用一份系统统一配置的 ChatGPT 订阅授权**（官方 “Sign in with ChatGPT”），供两位用户共享；不要求每位用户分别登录或绑定模型账号。App 自己的用户名密码只负责身份和权限。
- **不把按 token 计费的付费 API key 作为默认接入，也不在额度耗尽或订阅接入失败时自动切换到按量付费**；付费备选只有在显式开启时才会被使用。
- 服务端必须**先按内部用户 ID 和家庭 / 私人范围筛选上下文，再调用共享模型**，避免共享凭据导致两人的私人内容混在一起。
- AI 只“提议”记录，真正写入由服务端校验权限和业务规则后执行；模型调用失败不能绕过权限。

详见 [AI 层设计](../engineering/ai-layer.md)。

## 9. 推进与验收路径

| 阶段 | 内容 | 回答的问题 |
|---|---|---|
| **A. 可行性** | 两个内部用户 ID、用户名密码登录、会话恢复与家庭 / 私人隔离；默认模型提供方接入，图片与结构化输出小样；验证共享模型连接下私人上下文不串用。 | 身份、隔离与模型能力能否按既定边界工作（不建公开注册和自动找回）。 |
| **B. 本地交互骨架** | Flutter 三界面、本机数据模型、范围切换、记录卡、编辑 / 撤销和离线 outbox（待发送队列）；用假数据把三条流程跑顺。 | 交互是否顺手。 |
| **C. 服务端与 AI 闭环** | Rust API、PostgreSQL、原图存储与模型适配层；补齐权限校验、同步幂等、原图留存和变更记录，再跑真实文字 / 图片流程。 | 端到端是否可靠。 |
| **D. 两台手机终验** | 在两台安卓测试机上验证安装、各自聊天、家庭共享、私人隔离、离线排队与恢复；两台设备看到的范围和同步结果必须一致。 | 是否达到首版验收。 |

## 10. 首版范围之外

- iPhone 版（架构上预留，暂不构建）、电脑端查看。
- 公开注册、邮箱 / 手机号登录、自助找回密码。
- 从外部接口（银行、账单）自动拉取数据。
- 预算管理、月度消费额度。

## 11. 仍需细化（不阻塞先做验证）

- **内容与模板**：基础内容类型和 JSON 格式的具体约定，专用模板怎样建立和调整。
- **数据细节**：逻辑账户的移除方式、家庭成员资料时间线的呈现方式、同步冲突的处理体验。
- **使用验证**：各模型提供方的评测与降级顺序、图片与结构化输出效果、安装分发方式、两台手机的完整闭环。

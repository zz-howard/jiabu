ADR 风格的简表：每条一行，写明决定、日期和简短理由。需要展开的细节见对应文档。决策变更时追加新条目并标注取代关系，不修改旧条目的含义。

| P15 | 可选 App 级应用锁：生物识别或手势图案，数字 PIN 兜底；启动及后台超时返回时验证；开启后通知不显示内容、多任务缩略图遮挡；默认关闭 | 2026-10-26 | 防止手机被他人拿到时看到内容；不打扰不需要的用户 |
| P16 | 记错空间由用户手动移动：需同时是两个空间的成员；实现为原空间作废 + 目标空间新建，审计互相关联 | 2026-10-26 | 不破坏“记录可追溯”；AI 不跨空间推断 |
| P17 | 默认个人空间不可邀请他人、不可退出；需要共享就另建空间 | 2026-10-26 | 保证人人都有一个只属于自己的空间 |
| P18 | 空间最后一位所有者须先转让所有权或删除空间才能退出 | 2026-10-26 | 避免出现无人管理的空间 |
| P19 | 退出空间时，本机未上传的该空间内容提示后丢弃 | 2026-10-26 | 退出后已无写入权限，保留只会造成无法同步的数据 |
| P20 | 退出或被移除后，服务端对该账号按“空间不存在”处理（404，而非 403） | 2026-10-26 | 不暴露空间仍然存在 |
| P21 | 空间内容按模块划分（v1：账本、资料），成员按模块授权（不可见 / 只读 / 可编辑 / 可管理）；v1 不做授权界面、默认全开；无权模块视为不存在 | 2026-10-26 | 为家庭记忆、孩子参与等扩展预留：孩子可看记忆而看不到财务与健康资料 |
| P22 | 不区分成人 / 未成年账号类型 | 2026-10-26 | 能参与协作的孩子用普通账号即可，差异由按模块授权表达 |
| P23 | **AI 对话严格一对一**：每段聊天只有一位用户和 AI，不会有第三方加入；共同空间里每位成员各有自己的会话，互不可见、不能代答或停止；共享的是对话产生的记录，不是对话本身；AI 上下文只含发起者本人在该空间的对话历史 | 2026-10-26 | 对话里常有个人的想法和尚未确认的信息；一对一让权限、同步和交互状态都更简单，不存在多人抢答同一张追问卡 |
| P25 | **AI 问你分两种**：(1) **做到一半要你确认或补信息**（追问、不可撤销操作前的确认）：这条回复停在原地等你，回答记在卡片上、不是单独一条消息，回答后同一条回复接着做完、过程条不断开；等多久都行、换手机也能答；点停止或直接说别的事则作废（卡片“已停止”，不记账），久不回答会过期（时长待定）。(2) **回答写完了最后顺带一问**：你的回复是新消息，AI 回一条新的。取代 P24 中“你回答后这一行跟着变成‘已确认 / 已回答’”的继续方式（原先回答后由一条新回复继续） | 2026-10-26 | 用户感受到的是“AI 在做事，停下来问我一句，接着做完”；拆成两条回复会让过程断开、回答变成一条孤零零的聊天气泡 |
| P24 | **AI 回复顶部显示“过程”**：生成中逐行显示 AI 正在做的事（如“查本月餐饮支出 ✓ 0.8 秒”“对比上月 ⏳”），回答写完后自动收起成一行（“查了 3 项 · 用时 4 秒”），点按展开；每行是好懂的说明，不显示查询条件和原始数据，可带一句结果说明；某一步没查到只标那一行，不影响其他步骤和回答；需要确认的一步显示“等你确认”，确认卡在正文里；不显示 AI 的思考原文；过程只有本人看得到，不进复制、通知和搜索 | 2026-10-26 | 查数、对比要花几秒，用户需要知道 AI 在做什么、查了哪些；写完后收起，不和答案抢注意力；思考原文不可控，展示它帮助不大 |

|---|---|---|---|
| S1 | 服务端用 Rust：Axum + Tokio + PostgreSQL 18 | 2026-10-25 | 主流、资料最多；项目也有学习 Rust 的目标 |
| S2 | 新建公开 monorepo，客户端与服务端从零开始；服务端重写 | 2026-10-26 | 早期测试代码无保留价值；单仓便于接口与客户端同批改动 |
| S3 | 数据库访问用 SeaORM 2.0，锁定版本；关键查询配集成测试；特殊查询用 sea-query / 原生 SQL | 2026-10-26 | 原生 async、基于 sqlx 0.9；嵌套事务与 SQLx 同为 SAVEPOINT（已核源码）；实体类型减少 CRUD 样板 |
| S4 | 会话用不透明随机令牌（库存 SHA-256），不用 JWT；密码 Argon2id | 2026-10-25 | 需要随时吊销；两人规模无横向扩展需求 |
| S5 | 所有写入带幂等键；离线 outbox 推送；change_seq 游标增量同步；追加式审计 | 2026-10-25 | 离线重放不重复记账；可撤销、可追溯 |
| S6 | 一个请求 ID 贯穿客户端、服务端、AI 任务和审计表；JSON 日志，不记敏感内容 | 2026-10-26 | 拿一个 ID 就能定位问题 |
| S7 | 发布由 GitHub Actions 在打 tag 时构建：Releases 上的 aarch64 / x86_64 二进制 + GHCR 多架构镜像 | 2026-10-26 | 公开仓库的标准 arm64 runner 免费；原生构建，无需交叉编译 |
| S8 | 部署用 docker compose（服务端 + PostgreSQL 18）或 systemd，部署机不编译；作为常规服务部署，不依赖特定宿主环境 | 2026-10-26 | 可复现、易回滚 |
| S9 | 日常开发与测试在 x86 Linux 构建机上进行 | 2026-10-26 | Flutter 安卓工具链只有 x86_64 Linux 版；golden 需固定环境 |
| S10 | 数据模型以 `spaces` + `space_members` 为中心：业务表一律带 `space_id`，记录 / 资料 / 事件带 `created_by_member_id`；不再有范围枚举、`family_id` 或按 `owner_id` 判断可见性；所有查询按请求者的在册成员关系过滤，非成员一律返回 404 | 2026-10-26 | 对应 P10–P13；隔离只有一条规则，不可能漏判 |
| S11 | 同步按空间分游标：全局单调 `change_seq`，客户端为每个空间保存一个游标；新加入 / 重新加入的空间从 0 完整回填，退出的空间由客户端清除。幂等规则不变 | 2026-10-26 | 单一全局游标再按成员过滤会跳过新加入空间的历史，需要额外回填逻辑 |
| S12 | 审计事件记录 `actor_member_id` 与 `space_id`；登录等账号级事件只记 `user_id` | 2026-10-26 | 审计与空间成员模型一致 |
| S13 | 所有读写、同步、AI 上下文与导出只经一个授权函数 `authorize(member, module, action)`；内容表带 `module` 列与预留 `visibility` 列 | 2026-10-26 | 扩展模块与单条可见范围时不用改业务代码 |

## AI 层

| # | 决定 | 日期 | 理由 |
|---|---|---|---|
| A1 | AI 层 = 自有领域 trait（`ModelProvider`）+ `AiRouter` 配置路由与降级 | 2026-10-25 | 必须多模型可切换；业务不绑定任何第三方库 |
| A2 | 不用 Rig | 2026-10-25 | 框架面过大、破坏性变更频繁、无 namespace 工具；其 chatgpt provider 走非官方 backend-api（10-26 复查维持） |
| A3 | 多厂商引擎用 genai 0.7（锁定 `=0.7.1`） | 2026-10-26 | 原生 Anthropic / Gemini、国内厂商齐全、异步鉴权；10-26 复查未找到更好的替代 |
| A4 | 默认提供方 = ChatGPT 订阅，走官方 Sign in with ChatGPT；用 async-openai 自写适配器；其他提供方为降级备选 | 2026-10-26 | 复用已有订阅额度；genai 不支持 SIWC 的 namespace 工具和参数约束 |
| A5 | 不以付费 API key 为默认，不在失败或额度耗尽时自动切换付费；付费备选需显式开启 | 2026-10-26 | 产品需求的计费红线 |
| A6 | 模型输出一律经服务端 schema + 业务校验后才写库；上下文先按用户与范围过滤再调用（上下文部分已被 A7 取代） | 2026-10-25 | 共享凭据下防止私人内容串用；AI 失败不能绕过权限 |
| A7 | AI 按空间隔离：每个 AI 任务与会话带 `space_id`，上下文只从该空间组装；只写入当前空间，工具在服务端绑定任务的空间，模型无法指定其他空间；不推断、不建议其他空间；各空间聊天历史独立 | 2026-10-26 | 对应 P10；共享模型凭据下仍保证空间之间零泄露 |
| A9 | **Agent = ReAct 循环（思考 → 调用工具 → 看结果 → 再循环），架构按主 Agent + 子 Agent（主从）设计；v1 只有主 Agent，不用子 Agent，以后再加**（以后加时，委派是 ChatWeave 的委派步骤、子 Agent 的步骤嵌套在下面）。`ask_user` 与执行前需要确认的操作是**中断**：回复暂停，回答作为这次工具调用的结果（不是聊天消息），回答后同一条回复继续（P25）；最终回答里的问题按新消息处理。取代 A8 中“`ask_user` = 等用户、回复结束”的部分。暂停期间运行状态的保存与恢复另行设计（服务端持久执行设计，待定，另文），AI 层只约定“暂停 → 已持久化 → 回答后继续同一条回复”的契约 | 2026-10-26 | v1 先把单个 Agent 做稳；子 Agent 的界面与协议已由 ChatWeave 支持，以后加不改客户端。B/S 架构下服务端不会有线程一直等用户回答，持久执行需要单独设计 |
| A8 | **每个工具声明自己的步骤说明**（`step_label`，按模板生成，只填已授权的整理后名称）和可选的一行结果说明（`step_summary`）；Agent 循环在每次工具调用前后、`ask_user` 时发 ChatWeave 步骤事件（失败只标这一步并把错误回填给模型；`ask_user` = 等用户；停止 = 已停止）；提供方返回的推理 / 思考内容在适配器里丢弃，不进流、库和日志；工具名只进服务端日志 | 2026-10-26 | 对应 P24；说明由服务端写，用户看得懂，也不会把参数和原始数据带到客户端 |

## 聊天交互（ChatWeave）

| # | 决定 | 日期 | 理由 |
|---|---|---|---|
| G1 | 聊天回复采用 **Markdown 优先的混合式生成 UI**：默认是文字，信息适合结构化展示时插入语义块（记录卡、指标、表格、简单图表、状态、选项、确认、小表单）；块只含数据与含义，外观由客户端组件和手账主题决定 | 2026-10-26 | 多数回复是短句，文字最自然；需要看数、需要点选时组件更清楚；模型无法破坏设计系统 |
| G2 | **v1 就做流式**：文字逐步显示；组件块整块到达（先占位、后填满），不做组件字段级增量；稳定块 ID、按 ID 补丁、幂等事件、断线续传；最终消息服务端持久化并同步，重连 / 离线后以持久化版本为准 | 2026-10-26 | 不等整段生成完是基本体验；组件整块到达把复杂度控制在可验证范围；持久化版本优先保证多设备一致、离线可用 |
| G3 | 聊天交互做成**独立的开源库 ChatWeave，独立仓库**（[github.com/zz-howard/chatweave](https://github.com/zz-howard/chatweave)）：语言无关协议 + JSON Schema、Rust crate、Flutter 两层包（纯 Dart 核心 + 界面），不含任何家簿概念；家簿开发期用本地路径依赖，库发布后改版本依赖 | 2026-10-26 | 强制边界，避免记账概念混进通用聊天层；可复用；库用非记账的示例 App 跑测试与 golden |
| G4 | **v1 确定性映射，无 UI Agent**：服务端把 AI 结果按规则映射成语义块，客户端按块类型查注册表选组件；View 协议只保留到 Phase 2 | 2026-10-26 | 普通展示不额外调用模型：低延迟、低成本、可测试 |

## 待定问题（Open questions）

1. **Agent 运行时分期**：已定 v1 = 单个主 Agent（ReAct 循环）带工具，不用子 Agent（A9）；仍待定：子 Agent 什么时候加、先加哪些；v2 外部 Agent 网关（例如 Claude Code 类通用 Agent 接入）的时机。详见 [AI 层设计 · 第 12 节](../engineering/ai-layer.md#12-agent-运行时分期)。
2. **数据库迁移工具**：`sea-orm-migration`（迁移体可写原生 SQL）还是纯 SQL 文件 + 独立迁移命令。
3. **后台任务实现**：手写 Postgres 任务表，还是采用 apalis 1.x + apalis-postgres（刚发 1.0）。
4. **客户端发版流水线**：正式 APK 继续在构建机上构建签名，还是迁到 GitHub Actions（签名密钥的保管方式随之变化）；golden 在哪个固定环境里生成与校验。
5. **APK 分发渠道**：受保护的下载页、GitHub Releases 或其他；App 内“检查更新”放到 v2。
6. **降级提供方的选择与顺序**：以评测集结果为准；是否在任何情况下启用付费备选。
7. **SIWC 实测项**：`text.format: json_schema` 是否可用、图片输入与 namespace 工具的实际表现（见 AI 层接入验证清单）。
8. **家庭资料内容协议**：基础内容类型集合、JSON 格式、专用模板的定义与调整方式。
9. **数据细节**：逻辑账户的移除方式、家庭成员资料时间线的呈现、同步冲突的用户体验。
10. **对象存储**：v1 用本地磁盘；以后需要 S3 兼容服务时选哪个（MinIO 社区仓库已归档，Garage / SeaweedFS 未核实）。
11. **拍照 / 选图插件**：Flutter 端选型未定；上传前统一转 JPEG。
12. **PostgreSQL 行级安全（RLS）**：是否以空间成员关系为条件，作为应用层成员过滤之外的第二道防线。
13. **字体回退链**：`fontFamilyFallback` 在真机上做数字 + 中文混排是否稳定；不稳定则改用按字符切 `TextSpan`。
14. **范围外功能的时机**：iOS 构建、电脑端查看、邮箱 / 手机号登录与自助找回。
15. **按空间分别加锁**：首版应用锁只锁整个 App；是否以后支持对单个空间额外加锁。
16. **重新加入时的显示名**：成员退出期间改过账号显示名，重新加入后沿用原空间内显示名还是更新为新名字（倾向沿用空间内显示名、允许本人修改）。
17. **聊天回复中的模块权限**：对话是一对一的（P23），一条回复只有提问者本人能看到，不存在“其他无权成员看到同一条回复”的问题。剩下的问题是：一条回复的块可能含账本或资料数据，将来成员按模块授权后，**本人**的某个模块权限被收回时，历史回复里含该模块数据的块怎么显示（整条隐藏、块替换为兜底文字，还是按块过滤）。v1 所有成员默认全开，暂不影响；倾向“按块标注模块、同步与流下发时按 `authorize()` 过滤”。
18. **ChatWeave 的发布节奏**：何时发布第一个版本、家簿何时从固定提交切到版本依赖；库的许可证（预计 MIT）在建仓时添加。
19. **服务端持久执行设计**（另文，待定）：回复暂停等用户回答时（可能几小时甚至几天），Agent 运行状态怎么保存、回答后怎么恢复并在同一条回复里继续（B/S 架构下服务端不会有线程一直等着；参考 Temporal 一类的持久执行方式）；含追问过期时长、崩溃后恢复、与 `ai_jobs` 的关系。
